## Project

`hypeGRL` is a Python library for Graph Representation Learning in hyperbolic (and Euclidean) spaces. Its key contributions are:
1. A unified encoder-decoder framework across multiple embedding methods and geometries
2. Principled handling of **partially observed graphs** (unknown edges) via joint optimization — rather than zero-imputing missing entries, unknown edge weights are treated as free variables optimized jointly with embeddings

The Python package is `hypegrl` (all lowercase), installed from this directory.

## Architecture

The library is organized around the encoder-decoder formalism. Every method encodes a graph into a low-dimensional manifold and defines a decoder that reconstructs pairwise similarity. Unknown edges are handled uniformly across all gradient-based methods.

### Core abstractions

**`hypegrl/embedders/base.py` — `HyperbolicEmbedder` (ABC)**
All embedders inherit from this. The mandatory interface is:
- `fit(G, unknown_edges, X_init)` — encode the graph into embeddings. `X_init` is either `(N, d)` coordinates in the method's native input chart (ball for most, hyperboloid for Lorentz) **or a `Representation`** (any chart — re-charted into the optimisation chart via `from_polar`).
- `embeddings()` → `(N, d)` **Poincaré-ball** coordinates (the interop chart — plotters/downstream; saturates past `r≈12`)
- `embeddings_representation()` → the fitted `Representation` (exact geometry, chart-agnostic via its `to_polar`/`to_ball`/`to_hyperboloid`); concrete base method backed by `self._rep`, `None` before `fit`
- `structural_similarity(G)` → `(N, N)` — the target the encoder tries to match (e.g., adjacency matrix, forest matrix)
- `decode(X)` → `(N, N)` — the decoder output (e.g., connection probabilities). `X` is coordinates **or a `Representation`** (distance-based decoders use the exact `rep.dist()`; the curvature-aware Hydra decoders coerce a rep to ball, so `decode(rep) == decode(embeddings())`).

There is **no `distance()` method** — the loss is not part of the ABC. Each embedder expresses its loss as an inline `loss_fn(rep, A)` closure (typically a `_loss_from_dist(rep.dist(), …)` helper) passed to the optimiser; see below.

Capability flags (`is_gradient_based`, `is_generative`, `supports_update`, `supports_node_update`) let callers query what a method supports without try/except.

**The `Representation` abstraction (`hypegrl/representations/`)** — the swappable *chart* an embedding is stored and optimised in, orthogonal to the method. Canonical hub is **polar `(r, v)`**; subclasses `PolarRepresentation` (default for neutral methods), `BallRepresentation`, `HyperboloidRepresentation`, `TangentRepresentation` (opt-in `representation="tangent"`), `ExactPolarRepresentation` (`"exact_polar"`) and `CurvedPolarRepresentation` (`"curved_polar"`, which makes the metric axis continuous) — see their design notes below. Chart-specific options travel in one place, the `representation_kwargs=` constructor dict (e.g. `{"chart_curvature": 0.1}`, `{"max_norm": 1e3}`); no `from_polar` takes `**kwargs`, so an option the selected chart does not name raises `TypeError` rather than being silently dropped. Interface: `from_polar`/`to_polar`/`parameters`/`dist` per subclass; the base provides `from_ball`/`from_hyperboloid`/`to_ball`/`to_hyperboloid` via the exact converters (`manifolds/conversions.py`). Every gradient embedder takes a `representation=` constructor arg selecting the chart: **polar** for the neutral methods (`PoincareMaps`, `HyperMap`, `DMercator`, `HydraPlus`), the **eponymous** chart for `PoincareEmbeddings` (`"ball"`) and `LorentzEmbeddings` (`"hyperboloid"`). Polar is numerically robust at the large radii real graphs need (see the representation refactor design notes). **Known caveat**: the polar optimiser step is *not* the true Riemannian gradient of H^{D+1} (product metric + product retraction, not the warped-metric geodesic) — same minima, different path. The exact warped-polar `geoopt.Manifold` now exists as the opt-in `representation="exact_polar"` (`ExactPolarRepresentation` / `WarpedPolarHyperboloid`), but it does **not** supersede this caveat: it fixes the geometry without uniformly improving the optimisation — see the exact-polar design note below. **Practical consequence — the polar chart is scaled differently from ball/hyperboloid under a shared `lr`, so the default `lr_X=1e-2` (tuned in the ball/Riemannian era) can *under-drive* it.** Because the radial coordinate is a plain `Euclidean` parameter (not a point moving under the warped hyperbolic metric), a fixed `lr` produces a different effective geometric step than `RiemannianAdam` on the ball. Two faces of the same mismatch, both traced this session: (1) *under-convergence at small radius* — `PoincareMaps` on `balanced_tree(2,3)` at `lr_X=1e-2` plateaus (loss ≈ 3.9 at 500 steps) while ball reaches its basin fast; bumping to `lr_X≈3e-2` (or more steps) lets polar reach a *deeper* basin (≈ 0.19) that ball never finds — averaged over seeds polar is actually better, seed 0 is just a slow-converging worst case (this drove the `streaming` tutorial to `n_steps=500`); (2) *overshoot* — **restated, the old rationale was wrong**: it is not that "the angular gradient scales `~sinh²r`" (that is plain-GD reasoning; `RiemannianAdam` divides gradient magnitude out, and the sphere block is pooled into one scalar per node, so every node turns by `‖δv‖ ≈ lr` per step *independent of its radius* — measured: `Δθ` identical to 4 digits at `r=0.5` and `r=12`). Two real consequences. (a) *Angular resolution*: a node needing a correction below `lr` overshoots it immediately. (b) **The sharp one — no single `lr` serves a spread of radii.** Node `i` travels arc `lr·sinh(r_i)`, so outermost:innermost is `≈ e^(r_max−r_min)` (OpenFlights `r ∈ [19,41]` ⇒ `3.6e9`): tune for the outer nodes and the inner ones don't move, tune for the inner and the outer are flung across the space. **This is a property of the *spread*, not the magnitude — a graph at one uniform radius is unaffected however large `r` is (a same-radius toy converges at every `lr`, faster at larger `lr`, and demonstrates nothing).** Caveat: read the spread over the radii that *carry the loss* (leaves contribute ~nothing), so the operative squeeze is weaker than the literal extremes suggest but still exponential. Full derivation + the OpenFlights numbers: `hypeGRL_cicada/charts_as_warped_metrics.pdf` (§7 and Prop. "no global learning rate", App. C). We deliberately keep `lr_X=1e-2` as the neutral default (it is safe and polar is the robust general chart), and tune per-tutorial where a short step budget exposes the gap; a per-chart default `lr` (or the planned warped-polar manifold) would remove the need. Not a quality regression — a step-size scaling, characterised, not yet defaulted-around.

**`hypegrl/inference/` — `riemannian_optimize()` (fixed target) and `joint_optimize()` (unknown edges)**
Both consume a `Representation` (never bare coordinates). Gradient embedders delegate to one of them from `fit()`:
- `riemannian_optimize(representation, s_A, loss_fn, …)` — precomputes the fixed structural target `s(A)` once; optimises `representation.parameters()` (which may span several manifolds, e.g. polar's `Euclidean` radius + `Sphere` direction) by `RiemannianAdam`. Loss is `loss_fn(rep, s_A)`.
- `joint_optimize(G, representation, loss_fn, unknown_edges, …)` — rebuilds the adjacency `A` from the current `a_Omega` estimate **each step** (sigmoid-reparametrised, initialised via `imputation.compute_a_omega_init()`), optimising `representation.parameters()` + `a_Omega` jointly. Loss is `loss_fn(rep, A)`.

The loss receives the **representation** (not a bare distance matrix), so the decoder pulls what it needs — `rep.dist()` today (a future `rep.inner()` for RDPG-style decoders) — keeping `L(s(A), decode(X))` chart-agnostic. Each embedder does `if not unknown_edges: riemannian_optimize else: joint_optimize`. Adding a new gradient-based embedder means writing a `loss_fn(rep, A)` (via `rep.dist()`), building the chosen `Representation` from the warm start (`representations.build_representation`), and calling the two optimisers — then reading back `self._X = rep.to_ball()` and `self._rep = rep`.

### Manifold helpers

**`hypegrl/manifolds/poincare.py`** — shared `POINCARE_BALL = geoopt.PoincareBall()` instance (curvature `c=1`), plus coordinate conversion utilities (both NumPy and Torch/autograd versions):
- Poincaré ↔ H² polar (2D)
- Poincaré ↔ hyperspherical (d-dim)
- Poincaré ↔ Lorentz/hyperboloid

**`hypegrl/manifolds/lorentz.py`** — `StableLorentz` (a `geoopt.Lorentz` subclass) plus the shared `LORENTZ = StableLorentz()` instance (curvature `k=1`). `StableLorentz` clamps each point's spatial norm `‖x'‖` to `max_norm` inside `projx` and the retraction (`expmap`/`retr`), so every `RiemannianAdam` step (via `retr_transp → retr`) stays bounded. This prevents the hyperboloid `NaN` failure — one high-lr `expmap` step scales coords by `cosh(‖v‖_L)` and overflows `x_0` — mirroring the reference impl's `set_dim0` renorm (which uses `1e2`). The clamp is overflow-safe (factors out the max coordinate, so an inf-squared-norm point projects onto the boundary in-direction, not to the origin) and keeps the previous point on a non-finite step. **`max_norm` is not just a safety valve — it also regularises spread**: a sweep showed `≲30` binds below the natural radius and hurts, `≳1e6` lets the fit run away and degrades quality (trees collapse at high lr), with a usable window `~1e2–1e4`; **default `1e3`** (Poincaré radius `≈0.999`) dominated the reference's `1e2` (equal on trees that never reach it, `+0.8` AUC on denser graphs that do). **No reference prescribes the clamp, let alone the value**: the paper introduces no norm bound at all and argues (§3.2) that the Lorentz distance *avoids* the Poincaré fraction's instabilities — its only numerical device is the near-origin init. The clamp follows the reference impl; `1e3` is ours. It is a constructor arg here, and reaches a fit as a **chart option**: `representation_kwargs={"max_norm": ...}`, since it acts through `projx`/`retr` and so belongs to the chart that steps on the hyperboloid (`HyperboloidRepresentation` builds the instance). `LorentzEmbeddingsEmbedder` deliberately does **not** take it as a constructor arg — see that method's note. Defined on the manifold (not in an embedder) so any future hyperboloid method can reuse it; the D-Mercator Lorentz attempt was abandoned for exactly this overflow (it refines on the Poincaré ball instead — see that design note).

### Parameter estimation (`hypegrl/inference/parameters.py`)

**Scope / where estimators go.** This module is the single home for estimating the **scalar hyperparameters of the latent-geometry model** from an observed graph — the quantities a method needs *before* it embeds (e.g. HyperMap / E-PSO's `(m, L, γ, T, ζ)`). It is deliberately method-agnostic and imports no embedders, so any method can reuse it.

Decision rule for what belongs here:
- **Belongs here:** anything that maps a graph (or its degree sequence / clustering) to a scalar model parameter — `γ` (power-law exponent), `k_min` (power-law cutoff), and, when added, `T` (temperature, via clustering matching) and the `m`/`L` average-degree heuristics.
- **Does *not* belong here:** estimating the *unknown adjacency entries* `a_Ω` (that is `imputation.py`), solving for embeddings (`joint_optimizer.py` / `riemannian_optimizer.py`), or anything specific to one embedder's warm-start pipeline (e.g. the greedy init in `_hypermap_init.py`, the κ/β inference baked into `_dmercator_init.py`).

Current contents:
- `estimate_gamma(G, k_min=None, fallback_gamma=DEFAULT_GAMMA)` — discrete power-law MLE (Clauset–Shalizi–Newman, arXiv:0706.1062, §3.2). `k_min=None` (default) selects the cutoff automatically by KS minimisation; an explicit integer uses that cutoff directly. When no cutoff can be selected (`choose_kmin_ks` returns `None`: < 3 distinct degrees, or no cutoff with a well-supported tail), it warns and returns `fallback_gamma` (`DEFAULT_GAMMA = 2.5`, a neutral scale-free value; chosen over fitting because the `k_min=1` MLE can return an invalid `γ < 2`). Also importable as `hypegrl.embedders.hypermap.estimate_gamma`.
- `choose_kmin_ks(degrees, min_tail=DEFAULT_MIN_TAIL)` — CSN §3.3 KS-minimising choice of the cutoff. Candidates are the distinct degrees **with the largest dropped** (following the `powerlaw` package's `find_xmin`): the max-degree cutoff has a single-value tail that any distribution fits perfectly (KS=0), so scoring it spuriously wins (this was giving trees a meaningless `γ≈6.5`). Candidates whose tail retains fewer than `min_tail` degrees are also skipped (`DEFAULT_MIN_TAIL = 50`, CSN §3.2's "n ≳ 50 for reliable estimates" rule of thumb; used as a hard candidate filter is our choice). Without it, pure KS-min drifts into the sparse upper tail of a bell-shaped sequence and reports a spuriously steep `γ` off a handful of points. **The floor bounds tail size, not `γ` — the exponent is left uncapped, because HyperMap/E-PSO admits any `γ ≥ 2` (β = 1/(γ−1) ∈ (0,1]); we deliberately do *not* adopt `powerlaw`'s α ≤ 3 normalizability cap, which would reject legitimate `γ > 3`.** Returns `{k_min, gamma, ks, n_tail}` (large `ks` ⇒ not really a power law, e.g. a tree), or `None` when there are < 3 distinct degrees or no candidate reaches `min_tail` (pass `min_tail=1` to disable). Consequence: graphs too small for a 50-degree tail (e.g. karate, N=34) now return `None` → `estimate_gamma` falls back.
- `power_law_gof(degrees, n_bootstrap=1000, seed=None)` — CSN §4 semiparametric-bootstrap goodness-of-fit for the power-law hypothesis; **user-called, never automatic**. Returns `{p_value, plausible, D, k_min, gamma, n_tail, n_bootstrap}` with `plausible = p_value >= 0.1`, or `None` when the data can't be fit (`choose_kmin_ks` → `None`). Small `p` **rejects** the power law; large `p` only means it's *plausible*, not correct/best. Robustly rejects body-dominated non-power-laws (trees, `p≈0` across seeds) and passes true power laws (BA, zipf). **Known method limitation (not a bug):** a bell-shaped sequence (Poisson/Erdős–Rényi) is *not* robustly rejected — its sparse upper tail is weakly power-law-compatible, so the single-distribution GOF can call it plausible. Discriminating power-law from such an alternative is the job of a likelihood-ratio test (e.g. `powerlaw`'s `distribution_compare`), which we don't implement.

The E-PSO temperature `T` is **not** estimated here — see the `HyperMapEmbedder.estimate_temperature` design note below. Planned for this module: the `m` / `L` average-degree heuristics (both pure graph → scalar).

## Key design notes

- **Node ordering — the uniform `nodes()` accessor**: every embedder exposes `emb.nodes()` (a method on the base `HyperbolicEmbedder`, backed by `self._nodes`, set in `fit`) returning the node labels in `embeddings()` row order — `None` before fit. Reordering methods report their order (`HyperMapEmbedder` sorts by degree during greedy init; `DMercatorEmbedder` has its own order); non-reordering methods (`PoincareMapsEmbedder`, `Hydra`, `HydraPlus`, `PoincareEmbeddings`) return `list(G.nodes())`. This replaced the old per-embedder heterogeneity (HyperMap's `nodes_sorted` property, DMercator's `nodes` property). Consequence (a real silent footgun): `plot_poincare_graph`/`plot_polar` and any adjacency you build to pair with the rows must use that order, else every node is drawn at the wrong point and the plot looks like noise — pass `nodes=emb.nodes()` and the plotters align internally (`nodes=None` assumes `G.nodes()` order). Documented in the base `nodes()`, `HyperMapEmbedder.embeddings()`, and both plotter docstrings.
- **HyperMap temperature estimation is post-embedding, not in `parameters.py`**: neither the HyperMap paper nor the official C++ estimates `T` (the C++ takes it as a required `-t` input). The E-PSO paper (ref [5], Papadopoulos, Psomas & Krioukov, IEEE/ACM ToN 23, 198 (2015), §V) *does*: its global connection probability (Eq. 10) is Fermi-Dirac in the hyperbolic distance, `p(x)=1/(1+e^{(ζ/2T)(x−R)})`, so its steepness is exactly `ζ/2T`. `HyperMapEmbedder.estimate_temperature(X=None, A=None)` reads `T` off a **fixed embedding** by a one-parameter logistic MLE of the edge indicator on `u_ij = x_ij − R_{max(i,j)}` (`p=σ(−s·u)`, `s=ζ/2T`, `T=ζ/2s`) — the max-likelihood form of the paper's binned "tail slope" read-off (our reformulation, not verbatim). Because it needs an embedding (chicken-and-egg with `fit`), it lives on the embedder, **not** in `inference/parameters.py`. `T` is an *output* (it characterises the network's average clustering and calibrates the connection-probability decoder), not a knob to improve the coordinates: the paper reports (its Fig. 5) that embedding *quality* is not significantly affected by the input `T`, so reading `T` off a single embedding made with any reasonable input already gives a good estimate. For a better, self-consistent value, set `self.T` to the result and refit a couple of times. (Distance-ranked link prediction needs no `T` at all; `T` only calibrates the probability values.) Verified to recover a known `T` to <1% on synthetic Fermi-Dirac graphs (`tests/test_embedders.py::test_hypermap_estimate_temperature_recovers_known_slope`). We deliberately chose this over clustering-matching (the D-Mercator-style route via `infer_kappa_and_beta`), which would fit `parameters.py` but needs an E-PSO generator we don't have.
- **Connectivity constraint**: `update()` raises `ValueError` if removing edges/nodes would disconnect the graph — a disconnected Laplacian produces a block-diagonal forest matrix that changes the problem character.
- **`update()` is currently warm-started refit**: both `PoincareMapsEmbedder` and `HyperMapEmbedder` declare `supports_update=True` but implement `update()` as a warm-started call to `fit()`. True incremental updates via Woodbury are planned but not yet implemented.
- **All tensors use `float64`**: the optimization is numerically sensitive; `torch.float64` throughout.
- **Hydra minimises *strain*, Hydra+ minimises *stress* — the two are different objectives, and the gap between them is exactly what the refinement stage buys.** `HydraEmbedder`'s eigendecomposition is the *exact* minimiser (Eckart–Young) of the strain `‖Â−A‖_F` on the cosh-linearised Gram matrices `A_ij = cosh(√k·D_ij)` — that linearisation is what turns the problem into a solvable eigenproblem, and it is why Keller-Ressel & Nargang title the method "strain-minimizing". It is read straight off the discarded spectrum (`√Σ_discarded λ_i²`), never from `Â`. The **stress** `√Σ_{i<j}(d_H−D)²` — the error in the actual distances, and the quantity one actually cares about — is computed afterwards as a *reported diagnostic* (the `stress` property) and is what makes Hydra comparable to Hydra+. The one place stress drives a decision in `HydraEmbedder` is `optimize_curvature`, a 1-D outer search over a strain-minimising inner solve. `HydraPlusEmbedder` then minimises the **raw (squared) stress** `Σ_{i<j}(d_H − D·√k)²` by Riemannian Adam; the square shares its minimiser with the rooted stress the `stress` property reports, but has a smooth gradient, where `d/dL √L = 1/(2√L)` blows up precisely as the fit approaches perfect. Neither is an RMS — there is no averaging anywhere.
- **Only `HydraEmbedder` is non-gradient; `HydraPlusEmbedder` is gradient-based, and neither supports unknown edges — for two different reasons.** `HydraEmbedder` is closed-form spectral throughout (`is_gradient_based() == False`) and has no optimiser to route `a_Omega` through. `HydraPlusEmbedder` uses that eigendecomposition only as its *warm start*, then refines with `riemannian_optimize` on a `Representation` (`is_gradient_based() == True`, `representation=`-parametric, records `self._rep`) — it is a gradient method in every sense the rest of the library uses the word. What blocks unknown edges there is the **structural target, not the optimiser**: `s(A)` is the shortest-path matrix, a combinatorial (min-over-paths) function of the adjacency, so no gradient reaches `a_Omega` however the coordinates are optimised — the same obstruction as Lorentz Embeddings' hard `K_{iz} < K_{ij}` neighbourhood test. Both therefore zero-impute with a warning, and `HydraPlusEmbedder`'s warning names the real cause ("the stress loss requires a fixed distance matrix").
- **The exact warped-polar manifold (`representation="exact_polar"`) — correct geometry, not a better optimiser; opt-in, not the default.** `manifolds/polar.py::WarpedPolarHyperboloid` is a real `geoopt.Manifold` implementing H^{D+1}'s true geodesic-polar geometry: the warped metric `g = dr² + sinh²(r)·g_{S^D}` (`inner`), the natural gradient `G⁻¹ = diag(1, sinh⁻²r·I)` (`egrad2rgrad` — the `/sinh²r` the product metric drops), and the exact geodesic as `retr`/`expmap`. `ExactPolarRepresentation` packs `[r, v]` into **one** `ManifoldParameter` — the warp couples `r` and `v`, so they cannot live on a `Euclidean`×`Sphere` pair as `PolarRepresentation`'s do (that pair *is* the product-metric approximation). The radius is stored raw (no softplus): the manifold keeps `r ≥ 0` itself and flips `v` to the antipode for a geodesic through the origin. **Numerics**: the exponential map is evaluated through `tanh r` and a log-space radius increment `Δr = log(C + ‖n‖) − log1p(tanh r₀)`, so no `e^r`/`cosh r` ever forms — verified exact against an independently-computed hyperboloid geodesic to ~1e-16, and still exact at `r = 80` where ball and hyperboloid are long dead. Two flagged engineering choices (ours, not from any reference): a `max_step` cap on the geodesic step length (bounds `cosh s`; with the correct metric the natural step is `≈ lr`, so it never binds — a valve, not a knob) and an `ε_warp` floor on `sinh²r` in `egrad2rgrad` (polar coordinates are genuinely singular at the origin, so a root node at `r=0` gets a bounded near-zero angular gradient instead of `NaN`). Transport is projection transport, matching `geoopt.Sphere`'s own choice — momentum only, `O(lr)` distortion per step; exact parallel transport (angular rescale `sinh r₀/sinh r₁` + in-plane rotation) is a noted refinement. **The empirical finding is the important part: the exact gradient is *not* uniformly better.** With `lr` now a true radius-independent geodesic step length, `PoincareMaps`/`n_steps=500` gives — on `balanced_tree(2,3)` — the *deepest basin of any chart* (1.155 at `lr=0.1`, vs polar's best 1.807 and ball's 1.542), but on `balanced_tree(2,5)` it **loses to product-metric polar at every `lr`** (best 35.8 vs 20.5), with a narrower stable `lr` window (degrades by `lr=0.3`; ordinary over-stepping, not a numerical failure — points stay finite). **Why:** hyperbolic volume grows like `e^r`, so separating two leaves at radius `r` by `Δθ` costs arc length `≈ sinh(r)·Δθ`; a *correct* step of length `lr` therefore makes glacial angular progress exactly where deep trees need it, while the product metric's "wrong" scaling moves angular *coordinates* at `~lr` regardless of radius — an accelerating preconditioner. Natural gradient ≠ fastest descent, sharpened by `H^n`'s exponential volume growth. Related: `component_inner` returns one **scalar** metric norm per point, so Adam gives radial and angular a single shared adaptive scale (and the `O(sinh⁻²r)` angular term is dominated by the radial one); a measured per-block variant (what `ProductManifold` does, and what the split-parameter polar chart gets for free) recovers most of the deep-tree gap (71→31 at `lr=0.01`) but forfeits the small-tree win and still loses to polar — we keep the scalar form as the coordinate-invariant choice that makes the step length exactly `lr`. So `polar` stays the default; `exact_polar` earns its place as a principled optimiser with an interpretable `lr`, the best small-graph basin, and a reference implementation of the true geometry to measure the approximation against. **That question is now settled on real graphs, and the answer is no: at airport-scale radii `exact_polar` does not move the embedding at all.** Measured on the D-Mercator refinement — the mechanism is the two step components vanishing *together*, which is sharper than the deep-tree story above. The angular coordinate can only change by `≈ lr/sinh(r)`, and a warm start from a method's own initialisation is already near-optimal radially, so `∂f/∂r` is small as well; neither component moves and the refinement is a no-op (`polar` and `tangent`, which have no angular ceiling, do move it). No `lr` rescues this — it scales both components alike. Two consequences: (a) `exact_polar` is a moderate-radius chart, not a large-radius refiner, and (b) it cannot serve as the "working reference" in a matched-metric comparison at those radii, so the clean ball/hyperboloid/`exact_polar` slice has to be run at moderate radius (r ≲ 7), where all three are also in range. Full derivation: `hypeGRL_cicada/exact_polar_manifold_derivation.md`; tests: `tests/test_representations_exact_polar.py`.
- **The curved polar chart (`representation="curved_polar"`) — the metric axis as a continuum, not three isolated points.** `CurvedPolarRepresentation` is `ExactPolarRepresentation` with the warp generalised to `w_c(r) = sinh(√c·r)/√c`, i.e. `WarpedPolarHyperboloid(chart_curvature=c)`. `c=1` reproduces `exact_polar` exactly (pinned bit-for-bit in `dist` *and* `expmap`), `c → 0` approaches `tangent`'s flat warp `w=r`, and `polar`'s product metric `w=1` is a cylinder, **not** in the family. Four design decisions, all deliberate:
  1. **The parameter is `chart_curvature`, never `curvature`.** `g_c` genuinely is a constant-curvature `−c` metric, but it is used as a *preconditioner*: `dist()` returns the curvature `−1` distance at every `c` (pinned by a test), so the objective is untouched and runs at different `c` are directly comparable. An embedder's `curvature=` means the space being embedded into — a different quantity. See the curvature-free note above.
  2. **`WarpedPolarHyperboloid` was generalised rather than subclassed**, with `chart_curvature=1.0` as the default, so `exact_polar` stays the default code path and its exactness is structural rather than tested-in. Internals: `inner`/`egrad2rgrad` written directly in `w_c`; `expmap` delegates to a private unit-curvature geodesic run in `ρ = √c·r` (a constant metric rescale leaves geodesics alone).
  3. **The manifold's `dist` is its *own* metric's, `d₁(ρ)/√c` — not the embedding distance.** Deliberate: a `geoopt.Manifold` whose `dist` disagreed with its `inner`/`expmap` is a trap for any later caller. So `CurvedPolarRepresentation` decodes via `polar_distances_torch`/`polar_distances_between_torch` and never via `self._manifold.dist` (which `ExactPolarRepresentation` still may, since at `c=1` the two coincide).
  4. **Default `c = 1/4`, derived not fitted, and the derivation states its own range.** The arc formula's angular factor `sinh(r)/w_c(r)² ~ 2c·e^{(1−2√c)r}` blows up below `1/4`, decays above, and at `1/4` is `½·coth(r/2) → ½`, radius-independent. ⚠️ Two bounds: it assumes the crowded regime `sinh(r)·δθ ≪ 1` where `∂_θd ≈ sinh r` (in the wide-gap regime the balanced chart is `polar`'s flat metric instead), and it is a *gradient-magnitude* argument that `RiemannianAdam` partly normalises away. So it is a starting point, not an optimum — our own runs picked `c≈0.1` on Carnivora/fabaceae_sub and `0.3–0.5` on Primates. **Sweep `c`; do not trust the default.**
  Tests: `tests/test_representations_curved_polar.py` — the geodesic is checked against an **independent** RK4 integration of `r'' = w_c w_c' θ'²`, `θ'' = −2(w_c'/w_c)r'θ'` derived from the metric, not from the `ρ` substitution. Measured en route: at `r=15`, `c=1` a unit-length step turns the angle by `~3e-8` rad — the `exact_polar` freeze, quantified (and `arccos` of the dot product has no resolution there; read the angle off the chord).
- **Chart options have exactly one source, `representation_kwargs`, and no `from_polar` takes `**kwargs`.** The dict was chosen over a `chart_curvature=` argument on all six embedders (dead weight in five of six signatures), and it incidentally made `max_norm`/`max_step` reachable from an embedder for the first time. **The second half is the load-bearing part**: the `from_polar`s used to end in `**_` so a caller could pass options without knowing the selected chart, which silently *discarded* an option the chart did not name — a fit then running with the default the caller meant to replace. Removing the catch-alls makes Python itself raise the `TypeError`, so no validation helper is needed (an earlier `check_representation_kwargs`/`representation_options` pair reconstructed by `inspect` was deleted once `max_norm` moved out of the embedder and nothing needed chart-agnostic passing any more). **The rule is only uniform because no embedder contributes options of its own** — the one that did (`LorentzEmbeddings.max_norm`) now lives in the chart that implements it. Re-adding an embedder-level chart option, or a `**kwargs` to a `from_polar`, brings back both the two-sources problem and the bug it caused.
- **The tangent chart (`representation="tangent"`) — the paper's Euclidean parametrisation, evaluated in polar.** `TangentRepresentation` stores the embedding as **one** plain `geoopt.Euclidean` `ManifoldParameter` `z = r·v ∈ ℝ^d`, so `r = ‖z‖` and `v = z/‖z‖`; under `RiemannianAdam` a `Euclidean` parameter reduces exactly to Adam (identity `egrad2rgrad`/`projx`, elementwise `component_inner`), which is the point — the optimisation is unconstrained. **Provenance**: Mishne, Wan, Wang & Yang, *The Numerical Stability of Hyperbolic Representation Learning*, ICML 2023 (arXiv:2211.00181), §4.1. It implements **Eq. (7)** `F_L(z) = (cosh‖z‖, sinh‖z‖·z/‖z‖)` — equivalently **Eq. (6)** `F_D(z) = tanh(‖z‖/2)·z/‖z‖`, the same map composed with the isometry `φ` — with **Eq. (9)** `z* = argmin_{z∈ℝⁿ} f(F_D(z))` as the optimisation problem. The identity the paper states immediately after Eq. (7), `d(0, F(z)) = ‖z‖`, is what makes `r = ‖z‖` exact rather than approximate.
- **Why it is called "tangent" and not "euclidean"**: the paper's own label is the *Euclidean parametrization* (`𝔼` in its tables), but hypeGRL already uses "Euclidean" for flat *geometry*, and this is a chart of H^{D+1} — `representation="euclidean"` would read as "embed in Euclidean space", which is precisely wrong. `"tangent"` names where the parameter lives (`T₀H^{D+1}`), matching how `ball`/`hyperboloid`/`polar` are named for their coordinate system. Two things the name glosses: we never form `exp₀(z)` anywhere in the code path (it names the parametrisation, not the computation), and `z` is the tangent vector under the *Riemannian* identification — in raw ball coordinates the tangent vector is `z/2`, which is the paper's Remark 4.1 "mysterious 2" and the reason Eq. (6) carries the `/2` where Eq. (7) does not.
- **Deliberate divergence from the reference — we evaluate the distance in polar, they evaluate it in the ambient chart.** The paper (§5.1) and the official code (`scripts/stable-hyperbolic`, `TreeEuclideanLiftPoincare`/`TreeEuclideanLiftLorentz`) compute pairwise distances *after* applying `F_L`/`F_D`, so they inherit the capacity limits their own §3 derives (Poincaré `r₀ ≈ 38`, Prop. 3.1; Lorentz `r₀/2 ≈ 19`, Prop. 3.2) and need a hard norm rescale at `thr = 1−1e-16` plus an `arccosh` clamp. We do not: `_polar()` reads `(‖z‖, z/‖z‖)` off `z` and routes through `polar_distances_torch`, which is algebraically Eq. (2)∘Eq. (7) rearranged into a sum of non-negative terms — the same function, exact to `r ≈ 350`. **Consequence: our large-radius behaviour is better than the paper's but not comparable to its published numbers**; reproducing its stability curves would need an opt-in ambient-chart path we deliberately do not have. One engineering choice of ours (not from the paper): a `1e-30` floor inside `r = √(Σz²)` so a node at the origin gets a finite `∂r/∂z` instead of `0/0`.
- **Where the tangent chart sits between the polar ones, and its `lr` caveat.** In exact arithmetic its gradients equal the polar charts' — same `h(z)` — so the difference is step scaling: a coordinate step `δ` moves the point radially by `δ` and angularly by an arc of `sinh(r)·δ/r`, i.e. between product-polar (`sinh(r)·δ`) and exact-polar (`δ`). *(Our derivation, not the paper's.)* The paper's own claim for the parametrisation is a gradient one: Lemma 3.4 with Theorem 4.2 give `‖∇h(z)‖ = Ω(δ‖∇f‖)` against the ball's `Ω(δ²‖∇f‖)` at `‖x‖ = 1−δ` — the `exp₀` Jacobian lifts the decay from `δ²` to `δ¹` (their Remark 4.3). **The paper's learning rates do not transfer, and must not be copied**: its protocol is *plain SGD* at `lr = 1` for 30 000 epochs (§5.1; the shipped `run_tree.sh` uses `lr` 10–100 for 50k–100k), where ours is `RiemannianAdam`, whose coordinate-normalised step makes those rates enormous. Tests: `tests/test_representations_tangent.py`.
- **Measured: the tangent chart needs no `lr` retuning, and wins big only for Lorentz Embeddings.** Sweep of 3 single-cell graphs (`ToggleSwitch`, `Olsson`, `MyeloidProgenitors`) × 5 methods × `lr ∈ {0.003, 0.01, 0.03, 0.1, 0.3, 1.0}`, seed 0, refined from the cached warm starts in `experiments/results/inits/` (105 runs; harness mirrors `tune_inits.py::refine_one`). **`lr`: unlike the polar caveat above, there is no mis-scaling to correct** — the existing `lr_X = 1e-2` already sits in the optimum band, the best rate is 0.003–0.03 in 13/15 cells, and the chart is *less* `lr`-tolerant than polar, not more (`lr = 0.3` collapses 4/15 cells, `lr = 1.0` collapses 8/15). Those collapses are ordinary over-stepping: **no run produced a NaN or a non-finite radius, at any `lr`** — consistent with `z` being unbounded, with no boundary to saturate and no `cosh r` to overflow. **Quality**: swapping the chart in at each method's existing recommended `lr`, Hydra+ (`+0.2`), D-Mercator (`+0.3`), Poincaré Embeddings (`−1.0`) and Poincaré Maps (`−0.6`) are all at parity — inside single-seed noise — while **Lorentz Embeddings gains `+8.9` mean F1 (`+10.6/+2.8/+13.2`), rising to `+14.9` at its best `lr`, with the final loss roughly halving** (e.g. Myeloid 1.79e4 vs 3.94e4). That is the expected mechanism and the paper's own thesis: the hyperboloid is the numerically worst chart (`cosh r` overflow, cancellation from `r ≈ 18`), and tangent replaces it with an unconstrained parametrisation plus the exact polar distance — so **making `tangent` the default for `LorentzEmbeddings` is the open recommendation**, pending a multi-seed confirmation (`refine_from_inits.py`, the 5 saved seeds). Two caveats: the `±1` deltas are single-seed and should not be read as ordering, and Poincaré Maps *decouples* — its tangent loss is far worse than polar's at every `lr` (e.g. ToggleSwitch 60 vs 11) yet its F1 is comparable, which is not yet explained.
- **The polar chart's `r = softplus(u)` is a deliberate radial taper, not just a positivity trick — and it is *not* the cause of the recorded polar under-drive.** `PolarRepresentation` steps `u` and reads `r = softplus(u)`, so the chain rule `dr/du = σ(u) = 1 − e^{−r}` rescales the radial step. Under `RiemannianAdam` (which normalises the step in `u` to `≈ lr` whatever the gradient) the radial displacement is **`≈ lr·(1 − e^{−r})`** — measured against the closed form to within 1% at every radius from 0.01 to 20, and now pinned by `tests/test_representations.py::test_polar_radial_step_is_tapered_by_the_softplus`. **Correction to an earlier note: the damping is 22% at `r = 1.5`, not 42%** — the 42% figure squared σ, which is plain-GD reasoning (one factor from the gradient, one from the chain rule) and is void under Adam, exactly the error class as the retracted "angular gradient scales `~sinh²r`" claim. Beyond `r ≈ 3` the taper is under 5% and it dies exponentially, so it does *not* compound with the angular-spread problem above (which is the operative one). **The taper earns its keep.** Both alternatives take full-size steps near the origin, where `v` is worst determined and a step across zero teleports the node to the antipode: a raw radius clamped at 0 has no gradient below the clamp and pins any node that crosses it (measured: 12/63 nodes on `balanced_tree(2,5)`, 18/77 on Les Mis, stuck at exactly `r=0`), while `r = |u|` has no dead zone but reflects through the origin. Measured on `PoincareMaps` with a per-variant `lr` sweep (5 seeds, best-over-lr): softplus 15.2 vs `|u|` 41.2 on `balanced_tree(2,5)` (5/5 seeds), 28.0 vs 29.0 on Les Mis (5/5), 0.77 vs 1.39 on `balanced_tree(2,3)` (4/5), tied on karate; `HydraPlus` is indifferent to all three (differences inside noise), so the effect is loss-specific, not chart-wide. **The hypothesis that this warp caused the `balanced_tree(2,3)` under-convergence is refuted**: removing the damping makes that plateau *worse* at every `lr` (mean over 5 seeds at `lr=1e-2`: 2.01 softplus vs 5.08 undamped), and only 2 of 15 nodes sit at a radius where the taper is even appreciable. That under-drive is the `lr`-scaling issue recorded above, not this. Documented on `PolarRepresentation`; the `parameters` column of the chart table in `representations/base.py` names the reparametrisation.
- **Representations are curvature-free by design; a rep holds its own `_manifold` only when that manifold has per-instance state.** The chart (`Representation`) is orthogonal to the *metric scale* (curvature), and they are handled in different layers. ⚠️ **"Curvature-free" is about the curvature of the space being embedded into — do not read `CurvedPolarRepresentation`'s `chart_curvature` as a counter-example.** That parameter is the curvature of the *optimiser's* metric, a preconditioner that never enters the loss; the embedding's own geometry stays `k=1` in every chart, exactly as below. The two are independent, which is why the argument is not called `curvature`. **Curvature is a global scalar, not a chart property:** H of curvature −c is isometric to the c=1 space under `d ↦ d·√c`, so it is fully **absorbable into the loss** — scaling `rep.dist()` by a distance-temperature `τ = √c` *is* changing the curvature. Hydra+ already exploits exactly this (`s_A = D·√k` optimised on the c=1 chart ≡ embedding at curvature k; see `_stress_loss_from_dist`); Fermi-Dirac folds the scale into `β`/`R̂`/`ζ`; the ranking losses set it implicitly via radial spread (and could gain an explicit `τ`). So **every rep fixes curvature `k=1`** (`POINCARE_BALL`, `StableLorentz`, `polar_distances`) and no `Representation` carries curvature; a uniform, optionally-learnable loss-layer `τ` is the planned way to make it first-class for all methods (see the TODO.md entry). Adding curvature to a rep would be redundant with the scale the loss already carries and would conflate "how points are stored" with "how big the space is." **Consequence for `self._manifold`:** a rep holds its own manifold instance only when that manifold carries *per-instance state*, and three do — `StableLorentz` (`max_norm`, a graph-dependent numerical clamp that also drives RiemannianAdam's retraction) and `WarpedPolarHyperboloid` (`max_step`, plus `chart_curvature` for the curved chart) — so `HyperboloidRepresentation`, `ExactPolarRepresentation` and `CurvedPolarRepresentation` each build a fresh instance per fit and store it. `PoincareBall(c=1)` / `Sphere` / `Euclidean` are fixed and parameterless, so `BallRepresentation` / `PolarRepresentation` reference the shared module-level singletons directly (and polar is not even a single geoopt manifold — it is `S^D × ℝ₊` with a functional distance, so there is no `self._manifold` to hold).
- **D-Mercator = faithful original init + hyperbolic refinement**: `embedders/_dmercator_init.py` (`dmercator_init`) runs the full original D-Mercator pipeline — joint κ/β inference (clustering matching), S^D-corrected Laplacian Eigenmaps, likelihood-maximisation angular refinement, and final κ readjustment — to produce the warm start, mirroring how `_hypermap_init.py` provides HyperMap's greedy init. `DMercatorEmbedder.fit()` then builds a `Representation` from the native warm start `(v_i, r_i)` (chart chosen by `representation=`, **default polar** — see the representation refactor notes) and refines it with Riemannian Adam, minimising a Fermi-Dirac NLL on the exact hyperbolic distances `p_ij = 1/(1+e^{(β/2)(d_H − R̂)})`. `embeddings()` returns the ball image; the exact geometry is `embeddings_representation()` / `native_coordinates()`. β and R̂ are fixed from the init; the refinement moves both angular and radial coordinates, so the hidden degree κ (recovered from the final radius) is learned jointly with the angle. The init is binary-only (edge weights ignored) and treats β as inferred unless fixed in the constructor. Verified that `D=1` reduces to Mercator (`R = N/2π`).
- **β inference is bidirectional with a `β = D` floor**: clustering matching (`infer_kappa_and_beta`) raises β when the model under-clusters and lowers it toward the floor `D + 0.01` when it over-clusters, clamping (with a warning) when the target clustering is unreachable. Low-clustering graphs — trees, where `c̄_emp = 0` — drive β to the floor. This mirrors the reference C++ `infer_parameters(dim)`/`infer_parameters()`; an earlier one-directional "grow β only" bracket left β pinned at its random init on such graphs, corrupting μ/R̂/radial scale.
- **Stage-2 init: LE for all D by default; optional Mercator ordering-init for D=1**: the reference C++ uses LE only for D≥2 and the classic Mercator ordering + expected-angular-gap re-spacing for D=1. The `d1_init` constructor argument `DMercatorEmbedder(..., d1_init=...)` (and the `dmercator_init(..., d1_init=...)` function param) default to `"le"` (the paper's generalisation, used for all D); pass `d1_init="mercator"` to use `mercator_ordering_init` (the C++ D=1 init) instead. The flag is ignored (with a warning) for `d > 2`. On leaf-heavy graphs (trees) `"mercator"` spaces degree-one nodes deterministically around their hub while `"le"` reinserts each leaf at a random angle (MLE never moves leaves): measured on `balanced_tree(2,4)`/`(2,5)` over 8 seeds it gives a ~6–10× larger minimum inter-leaf angle and comparable-to-better reconstruction (AUC 0.83 vs 0.77 on `(2,4)`, ~tied on `(2,5)`). Default stays `"le"`.
- **⚠ The "purely numerical" framing below is confounded — the charts also differ in the metric the optimiser steps under.** Verified in geoopt 0.5.1: `BallRepresentation` and `HyperboloidRepresentation` wrap their coordinates in a `ManifoldParameter` on `PoincareBall` / `StableLorentz`, so `RiemannianAdam` calls those manifolds' `egrad2rgrad` — the *exact* hyperbolic metric, the same choice as `exact_polar` (w = sinh r) and a *different* one from `PolarRepresentation`'s product metric. So "polar wins decisively over ball/hyperboloid" varies representable range **and** preconditioner at once and cannot be attributed to either; the same applies to the D-Mercator radial-collapse writeup. Two further differences are geoopt's, not ours (and may change with a geoopt upgrade): `PoincareBall.retr` / `Sphere.retr` are the first-order `project(x + u)` while `Lorentz.retr = expmap` (geoopt ships `PoincareBallExact` / `SphereExact` if we ever want to remove that), and `Euclidean.component_inner` is per-coordinate while every other manifold used here gives Adam one scalar per point. Clean re-runs: hold the metric fixed and vary storage (ball / hyperboloid / exact_polar), or hold storage fixed and vary the metric (polar / tangent / exact_polar); a control at r ≲ 7 should collapse the first triple onto one curve. **Never compare charts at a shared `lr`** — a different metric *is* a different step size (this already produced one retracted claim). Accurate account now in `representations/base.py`'s module docstring.
- **Why D-Mercator defaults to the polar chart (the numerics behind `representation=`)**: polar, ball, and hyperboloid are all exact charts of H^{D+1} (each `Representation`'s `dist()` is the exact hyperbolic distance), so the choice is *presented below as* purely numerical (see the correction above) — and it matters because low-degree leaves belong at large radius `r ≈ R̂` (~16–20 even on tiny graphs, up to ~40 on larger ones). At those radii: the **hyperboloid** timelike coordinate `cosh(r) ≈ 1e5–1e7` overflows off the manifold during optimisation (fatal in the D=1/Mercator, leaf-heavy regime — NaN on most seeds of a Barabási–Albert tree); the **ball** stays bounded in (−1, 1) but *saturates* — `tanh(r/2) → 1` collapses every leaf past `r ≈ 12` onto the boundary, so their pairwise distances are wrong; the **polar** chart `(r, v)` keeps `r` a plain moderate number (no `e^r`, no saturation) and is exact at all radii. Hence **`representation="polar"` is the default** (`"ball"`/`"hyperboloid"` remain selectable, with those failure modes). An earlier Lorentz/`geoopt.Lorentz` refinement was abandoned for the overflow, which motivated the whole representation refactor; `tests/test_embedders.py::test_dmercator_robust_on_leaf_heavy_graph_d1` guards against a leaf-heavy NaN regression. (Full three-chart comparison: `experiments/representation_comparison.py`.)
- **Poincaré Embeddings has two interchangeable losses, default = ranking**: `PoincareEmbeddingsEmbedder(loss=...)` selects the encoder-decoder instantiation. `"ranking"` (default, the original Nickel & Kiela 2017 objective) decodes raw hyperbolic distances and minimises a soft-ranking NLL; its negatives are **re-sampled every step** inside the loss (`_loss_from_rep` → `ranking_nll_gathered`; `sample_negatives` draws `n_negatives` per node from the *known* non-edges `A_ik==0`, excluding self and imputed unknown pairs), so the loss is stochastic — tests compare smoothed loss windows, not `hist[-1] < hist[0]`. Each positive pair is weighted by `A_ij`, which is `1` for ordinary edges and the imputed value for unknown edges, so gradients reach `a_Omega` through the joint optimiser. `"fermi_dirac"` instead decodes the Fermi-Dirac edge probability `1/(exp((d_H−r)/t)+1)` and minimises Bernoulli cross-entropy (the same family as HyperMap/D-Mercator but with a single global `r`, `t`); only this mode reports `is_generative()=True`. `decode()` returns the distance matrix under `"ranking"` and the probability matrix under `"fermi_dirac"`.
- **Lorentz Embeddings = the Poincaré-Embeddings ranking objective on the hyperboloid (Nickel & Kiela 2018)**: same soft-ranking loss, different (numerically better) chart of the same space, with an exact-geodesic optimiser. `LorentzEmbeddingsEmbedder` embeds on `manifolds.lorentz.LORENTZ` (`StableLorentz`, the spatial-norm-clamped `geoopt.Lorentz`, whose `expmap` is the paper's Eq. 9), so intrinsic dim `d` uses `d+1` ambient coords. Near-origin init is Eq. 6 (`x' ~ U(-init_scale, init_scale)`, `x_0 = sqrt(1+‖x'‖²)`, `init_scale=1e-3` per the paper). `embeddings()` returns the **Poincaré-ball image** `(N,d)` via the Eq. 11 isometry (`lorentz_to_poincare`) so it drops into the disk plotters and the rest of the library; raw `(N,d+1)` hyperboloid coords are on `hyperboloid_embeddings()`, and `X_init`/warm-start (`update()`) use the hyperboloid representation, not the ball. **Similarity generalisation**: `structural_similarity` is the *weighted* adjacency `K`, and the negative set is the paper's `N(i,j)={z: K_{iz}<K_{ij}}` (less-similar nodes), which collapses to Poincaré Embeddings' non-edges on a binary graph — this is how weighted graphs are supported. **Unknown edges (the key design call)**: the `K_{iz}<K_{ij}` membership test is a non-differentiable hard threshold (same obstruction that blocks Hydra's shortest-path target from routing unknown-edge gradients), so (1) unknown pairs are excluded from every `N(i,j)` — negatives come only from *known* structure, keeping `a_Omega` out of the combinatorial part — and (2) positives are weighted by `K_{ij}` **only when `Omega` is non-empty** (`_loss_from_rep` sets `weighted = len(unknown_edges) > 0`), which routes a smooth gradient to `a_Omega`. Consequence: with `Omega={}` the loss is the paper's *unweighted* Eq. 12 exactly (binary *and* weighted graphs); the `K_{ij}`-weighting is hypeGRL's device confined to the unknown-edge regime the paper never covers (and a no-op on binary graphs). **Difference from the paper**: optimiser is geoopt `RiemannianAdam`, not the paper's exact-geodesic Riemannian *SGD* (Algorithm 1) — geometry still exact, update rule Adam, matching the rest of the library. Ranking-only (the paper's sole loss); no Fermi-Dirac variant, so `is_generative()=False` and `decode()` returns the Lorentz distance matrix. **Verified against the theSage21 PyTorch reference** (`scripts/lorentz-embeddings`): its `N(i,j)` (`pairwise[i,x] < min`) and unweighted-positive loss confirm our similarity-generalisation and `Omega`-gated weighting; it treats the matrix as a *directed* DAG and samples one positive per anchor per epoch (minibatch SGD), where we sum symmetrically over all edges full-batch (closer to the paper's symmetric Eq. 12). **Defaults `lr_X=0.3` / `n_steps=2000` are tuned, not paper values**: leaves must reach large radius for generality=norm to emerge, and a timid rate leaves the embedding under-spread (~5-10 AUC points worse on trees/karate/Les Mis). This aggressive rate is only safe because of the `StableLorentz` clamp — without it, `lr_X≳0.5` NaNs (the reference guards the same way via `set_dim0`). **That clamp is a *chart* option, not an embedder one**: `max_norm` acts only through `projx`/`retr`, i.e. only on the optimisation, and `geoopt.Lorentz.dist` is inherited unclamped (measured: identical distances at `max_norm=1e3` and `10`), so it means nothing to a chart that does not step on the hyperboloid. It is therefore set as `representation_kwargs={"max_norm": ...}` (default `1e3` comes from the chart), and `self.manifold` — used only by `decode()`/the `X`-based `distance()` — is the shared `LORENTZ`. **This was a real bug, not a tidy-up**: while `max_norm` was an embedder arg it was forwarded to *whatever* chart was selected, which the new strict option check turned into a `TypeError` on every non-hyperboloid chart — including `tangent`, the one this method most wants. Guarded by `tests/test_representation_selection.py` (all six embedders × all six charts). We deliberately skip the reference's lr burn-in (no measurable effect under Adam).
- **The ranking loss's training loop is `O(N·n_negatives)` per step, not `O(N²)` — via `Representation.dist_between`, not `dist()`.** Negative-sampling ranking loss only needs distances for real edges (`O(E)`) plus `n_negatives` sampled negatives per node/positive — but until this was fixed, both `PoincareEmbeddingsEmbedder` and `LorentzEmbeddingsEmbedder` computed the **full dense `(N,N)`** — internally `(N,N,d)` — distance matrix on *every* training step regardless, because `_loss_from_rep`'s closure called `rep_.dist()` (the zero-arg, always-full-matrix accessor) and only gathered from the result afterward. At N=4,267 (ogbl-ddi) this produced multi-GiB-per-step allocations and a CUDA OOM. The fix adds `Representation.dist_between(i_idx, j_idx)` — a new abstract method alongside `dist()`, implemented on all five charts, returning distances only for the given (broadcastable) index pairs without ever forming the `(N,N[,d])` intermediate. For `BallRepresentation`/`HyperboloidRepresentation`/`ExactPolarRepresentation` this is free — their underlying `manifold.dist(x,y)` (geoopt's `PoincareBall`/`StableLorentz`/`WarpedPolarHyperboloid`) is already elementwise/broadcastable, so `dist_between` just indexes the stored parameter before calling it (`ExactPolarRepresentation`'s packed `[r,v]` needs no `_unpack`-style renormalisation for this, since `projx`/`expmap` already keep `v` unit-norm on-manifold). `PolarRepresentation`/`TangentRepresentation` route `dist()` through `polar_distances_torch`, which is hard-wired to the `[:,None]`/`[None,:]` all-pairs outer product with no elementwise sibling, so `dist_between` uses a new `polar_distances_between_torch` (`manifolds/polar.py`) — the same law-of-cosines formula with the broadcasting brackets dropped. `ranking_nll_gathered`/`lorentz_ranking_nll_gathered` (`embedders/{poincare,lorentz}_embeddings.py`) are the new hot-path loss functions built on `dist_between`: positives via `torch.nonzero(A)` (an `O(N²)` boolean scan, not an `O(N²d)` allocation — cheap, and already the pattern `lorentz_ranking_nll_from_dist` used), negatives via `sample_negatives`/`sample_similarity_negatives` (`sample_negatives` is untouched, so its RNG consumption order — and therefore `random_state`-seeded test determinism — is exactly preserved; `sample_similarity_negatives` is chunked, see the next bullet). Verified bit-for-bit equivalent (`atol=1e-9`, same seeded negative draws) to the old dense `ranking_nll_from_dist`/`lorentz_ranking_nll_from_dist` on karate — this is the same math computed cheaper, not an approximation. **The old dense public functions (`ranking_nll`, `ranking_nll_from_dist`, `sample_negatives`, `poincare_distance_matrix`, and their Lorentz counterparts) are deliberately left unchanged** — they're the `X`-based standalone/test-facing API, not on the embedder's hot path, and rewriting them risked the pinned test contracts for no benefit. **Non-goal**: `structural_similarity()`/`A` stay dense `(N,N)` (used by `sample_negatives`'s `A==0` check and `joint_optimize`'s per-step rebuild) — sparsifying the adjacency itself is a separate, larger change; at ogbl-ddi's scale the dense `A` (~146MB) was never the problem, only the `(N,N,d)` distance computation was.
- **Lorentz's ranking loss scales per-*edge*, not per-*node* — so on a dense graph `dist_between` alone is not enough, and the loss is chunked + gradient-checkpointed.** This is the structural asymmetry between the two ranking embedders, and it only shows up on dense graphs. Poincaré's `sample_negatives` draws one negative row per **node** (`(N, n_negatives)`), but Lorentz's `N(i,j) = {z : K_{iz} < K_{ij}}` depends on the *edge's own* similarity threshold, so `sample_similarity_negatives` needs one row per **positive edge** (`(P, n_negatives)` with `P = nnz(A)`). On a dense graph `P` is itself `O(N²)`: ogbl-ddi (N=4,267, avg degree ~500) has `P ≈ 2.1M` directed edges, so at `n_negatives=50`, `d+1=11`, float64 the *per-edge* tensors dwarf the `O(N²·d)` dense matrix `dist_between` was introduced to avoid. Three distinct allocations had to be fixed, each of which OOM'd on an 11.6 GiB card in turn: (1) `sample_similarity_negatives`'s `(P,N)` boolean candidate mask (8.5 GiB) and its `float64` cast before `torch.multinomial` (70+ GiB); (2) `lorentz_ranking_nll_gathered`'s `(P, n_negatives, d+1)` negative-distance intermediate inside geoopt's Lorentz `dist` (8.75 GiB); and (3) — the subtle one — the *saved-for-backward* tensors of all chunks, which a plain Python chunk loop does **not** fix, because nothing is freed until the single `.backward()` on the summed loss, so chunking alone OOM'd identically to the unchunked version, one frame deeper. The fixes: both `sample_similarity_negatives` (`chunk_size=50_000`) and `lorentz_ranking_nll_gathered` (`chunk_size=10_000`) batch over positive edges, and each chunk's loss term goes through `torch.utils.checkpoint.checkpoint(..., use_reentrant=False)` (via the module-level `_lorentz_chunk_ranking_loss`) so its intermediates are recomputed in backward rather than held. All three are **exact, not approximations** — the per-row candidate math is unchanged, and summing chunk losses is a sum over disjoint edges — at the cost of the usual checkpoint recompute (~1.3–1.5× backward compute; measured, this is what makes the ogbl-ddi fit slow rather than infeasible). **One deliberate behaviour change**: chunking alters the order in which `torch.multinomial` consumes the RNG, so for a fixed seed the exact negative sample is not bit-identical across different `chunk_size` values (it *is* deterministic for a fixed `chunk_size`). Tests therefore pin the sampler's *contract* — every drawn index is a genuine candidate under the less-similar/known/non-self rule and its fallback chain, checked at both a forced multi-chunk and a single-chunk `chunk_size` (`tests/test_embedders.py::test_sample_similarity_negatives_chunking_preserves_candidate_validity`) — rather than an exact index sequence. **Consequence for method choice**: `LorentzEmbeddingsEmbedder` is inherently the more expensive of the two ranking embedders on dense graphs by a factor of ~`P/N` (the average degree, ~500 on ogbl-ddi), which is a property of the paper's edge-conditioned negative set, not an implementation defect. **Measured on ogbl-ddi (d=10, 1000 steps, seed 0), that cost does not buy accuracy**: Lorentz reaches Hits@20 valid 0.2605 / test 0.2173 in 6,747 s (2.41 GiB peak) against Poincaré's valid 0.2608 / test 0.2278 in ~82 s (4.34 GiB) — a dead heat on valid, ~1 point *worse* on test, for ~82× the wall time. Single seed, so the test gap is within plausible noise; the useful signal is the *absence* of a Lorentz advantage. This is the expected reading of the chart literature rather than a surprise: the hyperboloid's numerical edge (and the `tangent` chart's larger one, recorded above) shows up at **large radius**, and ogbl-ddi is a dense, low-hierarchy graph whose embedding never gets there. Both charts are exact charts of the same space optimised on the same objective, so on a graph that doesn't stress the radial range they land in the same basin. Treat "swap the chart" as a fix for a *numerical* symptom (NaNs, boundary saturation, `cosh r` overflow), not as a quality knob.

- **The hyperbolic advantage tracks hierarchy — measured, with a Euclidean control — but not monotonically, and the ogbl-ddi null was a property of the dataset.** ogbl-ddi showed no hyperbolic advantage (Poincaré Hits@20 test 0.2278; Lorentz 0.2173). It is also the least tree-like graph in `experiments/results/geometry_diagnostics.md` (δ_mean/diam 0.031, verdict *ambiguous*, mean degree 500 against 2–30 elsewhere), so the natural hypothesis was that the dataset, not the method, was the problem. `run_hierarchy_ladder` (`experiments/link_prediction_experiment.py`) tests it: three hierarchical graphs against a capacity-matched Euclidean RDPG/ASE control, 5 seeds, `q=0.9`, giant-CC-restricted, **paired** per-seed ΔAUC (both arms share the same prepared splits). Result — ΔAUC (Poincaré − RDPG), 5/5 seeds hyperbolic-wins in **every** cell:

  | dataset | δ_mean/diam | d=2 | d=8 | d=16 |
  |---|---|---|---|---|
  | wordnet/mammal_closure | 0.0010 | **+0.319** | +0.184 | +0.045 |
  | openflights | 0.0143 | +0.014 | +0.051 | +0.055 |
  | citation/Cora | 0.0187 | +0.188 | +0.128 | +0.114 |
  | *ogbl-ddi* (anchor) | *0.0308* | *−0.013* | *−0.033* | *−0.022* (d=16) |

  **The ordinal claim holds and the ddi null is explained**: Δ > 0 on all three hierarchical graphs at every dimension, Δ < 0 on ddi at every dimension — hyperbolic is *worse* than the Euclidean control there by AUC. **The ladder is not monotone in δ, and that was pre-registered as an expected possibility, not a disappointment**: OpenFlights has the *smallest* d=2 Δ (+0.014) despite sitting between the other two on δ/diam, and its Δ *grows* with `d` while the other two shrink. Non-monotonicity is consistent with the source literature — Chami et al.'s (2019, arXiv:1910.12933) own **shallow** Euclidean→Poincaré rows are also non-monotone in δ (their largest gain, +5.1 AUC, is on Cora, their *least* hyperbolic dataset); the strong δ-dependence is in their *GNN* rows, a different model class from hypeGRL's shallow embedders. **Confound to keep attached to this result**: RDPG/ASE decodes a dot product while the hyperbolic arm decodes a geodesic distance under a ranking loss, so part of Δ is decoder family, not curvature. The honest phrasing is "the hyperbolic distance decoder beats the RDPG dot-product decoder, and the gap is positive exactly where the graph is hierarchical" — not "hyperbolic geometry beats Euclidean geometry". The tightest control (not built) is a flat `Representation` running the identical loss/optimiser/negatives in Euclidean space. **ogbl-ddi is an anchor, not a fourth rung**: OGB supplies a fixed split and a *sampled* negative set (~10⁵ pairs) where the ladder scores every non-edge (~10⁶), and sampled negatives are a far easier discrimination (RDPG scores 0.975 there vs 0.762 on Cora), so only the within-dataset Δ transfers, never the absolute AUC.
- **δ does not by itself separate these graphs, and two of its normalisations disagree — report provenance alongside it.** `graph_stats.mean_hyperbolicity` is a Monte-Carlo estimate of the **mean** four-point δ over sampled quadruples; Gromov's δ is classically the **supremum**. The two are numerically incomparable, so our δ_mean and Chami et al.'s δ ∈ {0, 1, 3.5, 11} must never share a column (Cora is 0.0187 by ours and 11 by theirs). Worse, the ordering is normalisation-dependent: by δ_mean/diam the ladder is monotone (0.001 < 0.014 < 0.019 < 0.031, ddi worst), but by **raw** δ_mean ddi is 0.154 — *below* OpenFlights' 0.186 — because ddi's diameter is only 5. And the WordNet closure has **diameter 2** (the root is adjacent to every descendant), which bounds its four-point δ by construction, so its tiny δ is an artefact rather than earned tree-likeness. What actually separates ddi from the ladder is the composite `diagnose()` verdict plus a-priori provenance, which is why ladder rows carry a `provenance` string next to δ.
- **The WordNet mammal loader must emit edges in canonical order, or seeded splits are silently irreproducible.** `wordnet_mammal_closure_graph` builds its DAG by iterating a *set* of synsets, so while the node labels are deterministic (sorted synset names → `0..N-1`), the **edge insertion order** varied between processes. `link_prediction_split` draws one RNG value per edge in `G.edges()` order, so the same seed produced different splits per run — caught as a test that passed, failed, then passed again across three identical invocations. The loader now re-emits nodes and edges in sorted order; `tests/test_experiments.py::test_wordnet_closure_edge_order_is_canonical` pins it. **Related measured fact, and the reason the ladder embeds the closure and not the tree**: in a tree every edge is a bridge, so every held-out positive straddles two components of the training graph and the giant-CC restriction retains **0%** of positives — 0/108 through 0/127 across seeds 0–4, every time. The closure retains 99.6–99.9% (2–3 components; giant CC 1180–1181 of 1182). Nickel & Kiela (2017) likewise evaluate on the closure.
- **On these graphs F1@k and ROC AUC can disagree in direction; AUC is the headline and F1@k is kept only for continuity.** With ~10³ positives among ~10⁶ candidates, top-`k` F1 is dominated by the candidate-set size. On the WordNet closure at `d=2` the RDPG control scores **10.0% F1 against Poincaré's 1.8%, while its AUC is 0.507 — indistinguishable from random ranking — against Poincaré's 0.826**: it places a few hub-adjacent pairs at the very top and is uninformative everywhere else, which top-`k` F1 rewards and AUC does not. Read the two together; do not quote F1@k alone at this scale.

## Conventions (for contributors and Claude)

- **A long run writes as it goes, and its filename says which run it was.** Any experiment taking more than a few minutes persists partial results after each *unit of work* — each rate, arm or seed — never once at the end. Three costs, all paid here: an interruption otherwise loses everything (an 18-hour sweep killed at 11% survived only because that script wrote per-arm json); a misconfigured sweep is discovered hours in rather than minutes in; and "show me the curves so far" is simply unanswerable — a 2.5-hour run had nothing on disk 60% of the way through, which is what prompted this rule. Equally, the output stem must carry whatever distinguishes the run (graph, device, budget), or a second run silently overwrites the first: the same sweep on CPU and CUDA gives different stresses, so `two_stage_chart_schedule` tags its output with the device. Two concurrent runs of the *same* graph and device still collide — give one an explicit distinct output rather than racing them.
- **`experiments/` is tested for its inputs and invariants, not for its orchestration.** The rule below is written for `hypegrl/`, which has an API contract; `experiments/` explicitly has none, and applying the library's rule there produces filler — assertions that a three-line dispatch dispatches, or that a formula matches itself. Test the things whose failure is **silent and corrupts a number**: graph construction, data loading *and its ordering*, determinism, and the error paths that protect a long run (one `inf`-not-raise test costs 0.05 s and saves a 2.5 h sweep from dying at hour two). Do **not** test the sweep loop, the printing, or anything a first run reveals in ten seconds. The canonical example of the first kind is `test_wordnet_closure_edge_order_is_canonical`: a set-iteration edge order made seeded splits irreproducible, and it passed/failed/passed across three identical invocations — no amount of *running* the experiment would have found it.
- **All code ships with tests.** New code lands with its tests in `tests/` as part of the same change — a stub file with a `test_placeholder` is not coverage. An untested module is where the silent bugs live: `generation/fermi_dirac.py` sat at 0% coverage while capping every distance it computed at the Poincaré ball's `16.811243` ceiling, and nothing failed. When fixing a bug, write the failing test **first** and confirm it reproduces the defect before touching the code, so the test is known to have teeth. Run the full `pytest` before calling anything done and report the result honestly, including coverage for a module you added. If something genuinely resists testing (plot rendering, a multi-hour sweep, a GPU-only path), say which part and why rather than skipping it silently.
- **New public modules ship with an API-reference entry.** Autodoc is opt-in per module: a module reaches the rendered site only if some `docs/api/*.rst` (or `docs/methods/*.rst`) names it in an `automodule`/`autoclass` directive, and a missing entry produces no warning — the build just succeeds with a smaller site. `tests/test_docs_coverage.py` fails when a public, non-stub module has no directive anywhere.
- **Documentation reflects the present.** Comments and docstrings describe the code as it is *now* — no change history ("previously…", "for backward compatibility", "used to…"). Record *decisions* in this file, not in code comments.
- **Be explicit about extrapolation.** Keep a clear line between what a cited source (paper, reference code) actually says, what the task asked for, and anything added on top — home-grown heuristics, default values, thresholds, design choices. Don't attribute invented specifics to a source; when citing from memory rather than a checked reference, say so.
- **No hacky code, and "hacky" has a test rather than a vibe.** Every mechanism must be the *simplest thing that produces the required behaviour*, and a reader must be able to see why it is needed without being told a story about how it got there. This is a stronger demand than the readability rule below: that one is about how code reads, this one is about whether it should exist at all. Six checks, each from a real episode in this repo:
  - **Prefer the language's own mechanism to a reimplementation of it.** A validator built on `inspect.signature` to reject unknown keyword arguments reimplements what Python does for free; the real fix was deleting the `**kwargs` that had been suppressing it (net −39 lines, two fewer public functions).
  - **Never add a mechanism to compensate for another mechanism — remove the first.** A catch-all that silently drops arguments, plus a checker to catch what it dropped, is one design fighting itself.
  - **A parameter that does not apply everywhere it is passed is in the wrong place.** `LorentzEmbeddings.max_norm` was an embedder argument handed to charts with no such coordinate. The fix was moving it to the chart that implements it, not filtering it en route.
  - **Branching or filtering to make a value fit is a smell.** Code that asks "does the destination accept this?" is usually holding the value in the wrong hand.
  - **If the behaviour can only be explained by saying *who* supplied a value, simplify.** "Strict for the user's options, filtered for the library's own" was two rules where one would do.
  - **Prefer deleting to adding.** A change that removes more than it adds is usually the right one. Report the line balance when it does.
  Do not wait to be asked: when a simpler design exists, propose it in the same breath as the working one. Both cleanups above surfaced only because a reviewer asked what a word in a docstring meant and suspected glue code underneath — that is a review catching a smell too late, not a process working.
- **Readability over premature optimization.** This is research code: prefer clear code that reads like the math / pseudocode. Optimize only when asked, and state a change's true scope and readability cost honestly.
